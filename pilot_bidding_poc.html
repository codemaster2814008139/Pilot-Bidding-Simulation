Backend LLM proxy
Configure provider and model only in .env beside proxy_server.py: LLM_PROVIDER, ANTHROPIC_MODEL / OPENAI_MODEL, and API keys — see env.example. Run pip install -r requirements-backend.txt then python proxy_server.py; Ping backend shows the resolved model and whether the key matches that provider.
Manual copy‑paste workflows work without the proxy.
5 pilot profiles
Bidding unit:
10 flight pairings — circular routes, variable legs & days
20 monthly lines LINE MODE — 5 pairings each · 100 pairings total
Pay calculation method
Block pay = credit hours × pilot base pay rate ($/hr)
Credit hours = max(actual block hours, guaranteed minimum)
Guarantee = max(4.0h, number of legs × 0.5h) — protects pilots on short pairings
Per diem = TAFB (hours away) × $2.50 — paid on top of block pay
Total trip value = block pay + per diem
Choose LLM testing mode

The weighted oracle (ground-truth rankings) always comes from sliders on the Oracle weights tab — it does not depend on which LLM test you pick.

Here you choose how the LLM gets tested against that oracle: one prompt ranking everything at once, head-to-head comparison, or separate 0–100 scores per pairing.

A · Rank-all
The AI sees everything at once and sorts it.
  • The pilot's full profile and all options are given in one message
  • The AI returns a ranked list from best (#1) to worst in a single call per pilot
  • Simple and fast — fewest LLM calls of the three methods
  • Main limitation: on long lists the AI may lose track of earlier options, leading to inconsistent rankings across runs
B · Pairwise
Head-to-head matchups — like a mini tournament.
  • The AI is shown just two options at a time and asked: "which is better for this pilot?"
  • Much simpler per call — the AI stays focused without a long list to juggle
  • Votes feed into a ranking model (Bradley-Terry): if A beats B and B beats C, A is ranked above C even without a direct matchup — the model infers a consistent global order from partial evidence
  • To keep costs down, only the most informative pairs are asked: a quick first round reveals the rough order, then a second round focuses on the close/uncertain matchups only
  • More reliable on long lists, but requires more LLM calls than Rank-all
C · Scoring
Each option gets an independent score, like a rubric.
  • The AI rates each option separately on a 0–100 scale — one call per option
  • Each prompt includes a personalised calibration anchor: concrete examples of what 90–100, 45–55, and 0–15 look like for this specific pilot (e.g. "90–100 = home same day, preferred aircraft, report after 7 am")
  • The same option is scored in multiple independent runs; the final score is the average (or middle value of 3 runs) to smooth out random variation
  • Two options are marked tied if their score ranges overlap across runs — so a 72±8 and a 68±8 are treated as equivalent rather than forcing a false ordering
  • Easiest to scale: all calls are fully independent, so any number of options can be evaluated in parallel

      ▶ View prompt template (what the LLM receives)
      

        

          One prompt per pairing (or line) per pilot — each call is fully independent. The LLM scores a single pairing 0–100 using a calibration anchor derived from the pilot's profile. Scores are sorted externally to produce the final ranking.
        

        
You are evaluating how well a flight pairing fits a specific airline pilot's preferences.

== PILOT PROFILE ==
Name: Capt. {name}
Age: {age}  |  Family: {family status}
Aircraft qualifications: {e.g. B737, B767}
Preferred aircraft: {preferred type}
Base pay rate: ${base pay}/hr

== SCORING CALIBRATION ==
  90–100 (ideal): {e.g. "0 hotel nights, TAFB under 30h, B737, report after 8am, pay above $4,000"}
  45–55  (acceptable): {e.g. "1–2 hotel nights, TAFB 40–55h, report 5–7am, pay ~$2,800"}
  0–15   (unacceptable): {e.g. "wrong aircraft, TAFB over 70h, 2+ nights, report before 5am"}
  Weight priorities: TAFB (35%), hotel nights (25%), report time (20%), aircraft (10%), pay (10%)

  Pairing 5 — 3 legs, 1 night away
    Aircraft: Boeing 737 (B737) | Qualified: yes

Scoring — one call per pairing

      

        Each pairing is scored 0–100 for the selected pilot in a separate LLM call.
        Scores are sorted to produce a ranking compared against the oracle.

        In line mode:
        each complete monthly line is scored as a whole in one call —
        1 call per line per pilot (e.g. 20 lines × 3 pilots = 60 calls).
        The LLM evaluates the full monthly schedule holistically. Allocation uses these line scores directly.

How allocation works

    

      Pilots bid in seniority order (#1 most senior, gets first pick). Each pilot is awarded their highest-ranked available pairing that they are qualified for.

      LLM-based: builds each pilot's preference list from Evaluate data — in order:

      (1) Compare all at once JSON if present;

      (2) else Scoring (sort 0–100 scores across all pairings);

      (3) else Pairwise (win-count ranking after a completed round-robin). Each pilot needs at least one complete source; if several exist for the same pilot, the numbered priority above chooses which is used.

      Oracle-based: uses oracle weights to rank pairings per pilot. Always available as a baseline.

      If both are run, a side-by-side comparison shows where outcomes differ.
    

    

      LINE MODE Pilots bid on complete monthly lines (not individual pairings).

      Pilots bid in seniority order. Each pilot is awarded their highest-ranked available line that they are qualified for (all pairings in the line must be within their aircraft qualification).

      LLM-based: use either Compare all at once (line JSON) per pilot on the Evaluate tab, or run Scoring while still in line mode (scores every pairing that appears on the lines — allocation ranks lines by the sum of those pairing scores).

      Oracle-based: uses oracle weights applied to monthly statistics (total TAFB, nights away, pay, etc.).
